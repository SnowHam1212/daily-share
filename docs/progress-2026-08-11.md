# 作業記録 2026-08-11

トークルーム機能のリリース準備と、その過程で発覚したセキュリティ問題への対応。

## 1. トークルーム機能（#79 / マージ済み）

チャットを LINE 風の2画面構成（ルーム一覧 → ルーム詳細）に作り替えた。

**参加を同意制にした。** 位置情報と予定を共有するアプリなので、他人を勝手にチームへ入れられない設計にしている。

- 「招待 → 本人が承諾」の2段階（`team_invitations` テーブル、`0012`）
- 例外は招待コード参加。本人がコードを入力する操作なので同意済みとみなす
- 追放できる人はチーム作成時に `teams."removalPolicy"` で決める（`admin_only` / `anyone` / `nobody`）

あわせて以下を修正した。

- 退出を `leave_team` RPC に統一。最後の1人が抜けたらチームごと削除し、孤児ルームを防ぐ。最後の管理者が抜けたら最古参を管理者に繰り上げる
- 追放・退出に確認ダイアログを追加
- `is_team_member` / `is_team_admin` を `REVOKE`（membership oracle の防止）

## 2. 招待コードでの参加が壊れていた（#84 / マージ済み）

**正しいコードを入れても必ず「招待コードが存在しません」になっていた。** 原因は独立した2つで、どちらも壊れていた。

1. フロントエンドが `teams` を直接 SELECT していた。`teams_select` は所属チームしか返さないため、参加前は必ず0件になる
2. **本番に `join_team_by_code` 関数が存在しなかった。** マイグレーション番号 `0007` の重複により、履歴には記録済みなのに中身が適用されていなかった

`events.teamId` は `NOT NULL` で、`CalendarTab` もチーム未所属だと予定追加を弾く。つまり**カレンダーも実質使えない状態**だった。

`0015` で関数を入れ直し、フロントエンドを RPC 経由に修正した。

## 3. セキュリティ問題（#93 / #94 / #95 — レビュー待ち）

### 発覚したこと

**ログイン不要で以下が読み出せる状態だった。**

| テーブル | 内容 |
|---|---|
| `users` | 全21ユーザーのメールアドレス、電話番号、生年月日 |
| `teams` | 全13チームの招待コード |
| `user_teams` | 誰がどのチームに所属しているか |

招待コードが読める＝**誰でも任意のチームに参加でき、そのメンバーの位置情報と予定が見られる**。

さらに `user_teams_insert` も緩んでおり、**匿名で任意のユーザーを任意のチームに参加させられた**。同意制の設計がテーブル直叩きで完全に迂回できていた。

### 原因

- `teams_select` / `user_teams_select` / `user_teams_insert` … 動作確認のために `USING (true)` へ書き換えられ、**戻し忘れていた**
- `users_select` … `0001` の時点から `USING (true)`。緩められたのではなく元からの設計で、フレンド検索がこれに依存していた

### 対応方針

`users` は Instagram / X と同じ考え方を採った。**検索できること自体は問題ではなく、公開してよい情報（表示名）と絶対に出さない情報（メール等）を分けるのが本質。**

Postgres の RLS は行単位で列を制御できないため、

- テーブルへの直接 SELECT は「自分の行のみ」
- 公開情報だけを返す `SECURITY DEFINER` の RPC を用意

という形にした。**検索の使い勝手は変えずに漏洩だけ止まる。**

### 結果

匿名アクセスを全9テーブル × 読み書きで実測。**読み取りは全て0件、書き込みは全て `42501` で拒否**になった。
